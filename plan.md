# Product Studio Implementation Plan

**Status:** Proposed  
**Created:** October 11, 2026  
**Recommended direction:** Guided Product Studio with a lightweight evidence model

## 1. Objective

Create a separate visual product stream for product and technology teams to:

- Maintain reusable company and product context.
- Upload and reference relevant files and repositories.
- Run structured design-thinking exercises with agent assistance.
- Generate grounded, source-linked product artifacts.
- Review and approve decisions before generating engineering handoffs.
- Draft and optionally publish issues to approved GitHub repositories.

The new stream must not change, extend, or interrupt the existing Decision Room workshop flow.

## 2. Non-Negotiable Boundary

### Existing application remains unchanged

The Decision Room continues to provide:

- Public and anonymous access.
- The existing landing-to-completion stage flow.
- Private attendee commitments.
- Three options generated by one Foundry prompt agent.
- Independent Decision-1 ranking.
- The existing facilitator dashboard and workshop metrics.

The new stream must not reuse or modify:

- The workshop stage state in `client/src/App.tsx`.
- Anonymous workshop sessions.
- Workshop case definitions.
- Workshop prompts.
- Workshop API contracts.
- Workshop dashboard metrics.

### New companion product

The Product Studio will have:

- A separate route or application entry point.
- Authentication and workspace authorization.
- Persistent company and product context.
- Its own frontend state, API namespace, and database schema.
- Reviewed agent workflows with explicit human gates.
- Separate operational metrics and audit records.

Preferred deployment boundaries:

1. Separate application at `studio.<host>`.
2. Separate frontend bundle mounted at `/studio`.
3. Independent deployment initially, with shared infrastructure libraries where useful.

Option 1 provides the strongest isolation.

## 4. Context and Grounding Model

Use a relational model that can support graph-like relationships without requiring a graph database in the first release.

```text
Organization
  └─ CompanyProfile
      └─ Product
          ├─ ProductProfile
          ├─ Workspace
          │   ├─ Source
          │   ├─ GroundedClaim
          │   ├─ ExerciseRun
          │   ├─ Decision
          │   └─ Artifact
          └─ Integration
              └─ GitHubRepository
```

### Grounded claim fields

Every generated claim that may influence a decision should retain:

- Claim text.
- Source identifier and exact source location where possible.
- Source version or retrieval timestamp.
- Evidence classification:
  - `Observed`
  - `Reported`
  - `Assumed`
- Confidence.
- Applicable company, product, and workspace.
- Freshness date.
- Supporting and conflicting sources.
- Human validation status.
- Validating user and timestamp.

Documents and stakeholder statements remain reported evidence. They must not be presented as observed user behavior unless supported by appropriate research.

## 5. Agentic Workflow

Use a deterministic orchestration service. Do not allow unrestricted agent-to-agent delegation.

### Roles

#### Context assembler

- Retrieves the smallest relevant context packet.
- Preserves source references and permissions.
- Identifies missing, stale, and conflicting context.
- Does not generate product decisions.

#### DT Coach

- Facilitates the selected design-thinking exercise.
- Asks focused questions and manages the exercise stages.
- Separates team input, evidence, assumptions, and generated suggestions.
- Stops at an exercise review checkpoint.

#### PRD Builder

- Consumes only approved decisions and evidence.
- Generates an editable product requirements draft.
- Preserves links to sources and exercise outcomes.
- Does not automatically start delivery planning.

#### Functional Planner

- Consumes an approved PRD.
- Produces epics, capabilities, stories, dependencies, and acceptance criteria.
- Identifies unclear requirements rather than silently filling gaps.

#### GitHub adapter

- Reads repository metadata after authorization.
- Converts approved work items into issue drafts.
- Checks for likely duplicates.
- Publishes only after explicit confirmation.
- Returns created issue identifiers and individual failures.

## 6. Human Approval Gates

Required gates:

1. Approve the context snapshot used for an exercise.
2. Approve or revise the problem framing.
3. Select which ideas and conclusions survive.
4. Commit the exercise decisions.
5. Approve the PRD before planning.
6. Approve the functional plan before issue preparation.
7. Approve repository mapping and issue content.
8. Confirm the exact GitHub write operation immediately before publication.

An agent failure, rejected output, or missing approval returns the workflow to the previous editable state. It must not silently continue.

### Recommended workflow states

```text
DRAFT_CONTEXT
  → CONTEXT_REVIEW
  → EXERCISE_ACTIVE
  → EXERCISE_REVIEW
  → DECISIONS_APPROVED
  → PRD_DRAFT
  → PRD_APPROVED
  → PLAN_DRAFT
  → PLAN_APPROVED
  → ISSUE_PREVIEW
  → PUBLICATION_CONFIRMED
  → PUBLISHED
```

## 7. Technical Architecture

### Frontend

- React and TypeScript.
- A router and authenticated application shell separate from the workshop.
- Accessible desktop-first workspace UI with responsive support.
- Resumable exercise and review states.
- Source and provenance drawer available throughout the workflow.
- Clear visual distinction between:
  - Human-authored content.
  - Source-derived claims.
  - Agent-generated suggestions.
  - Approved decisions.

### Backend

- Separate API namespace, such as `/api/studio`.
- Authentication and workspace-level authorization.
- Workflow orchestration service.
- Context ingestion and retrieval service.
- Artifact generation service.
- GitHub integration service.
- Audit and observability service.

### Persistence

Introduce a durable database for:

- Organizations and users.
- Membership and roles.
- Company and product profiles.
- Workspaces.
- Sources and source versions.
- Claims and evidence relationships.
- Exercise runs and contributions.
- Decisions and approvals.
- Generated artifacts.
- Integration configuration.
- Issue drafts and publication receipts.
- Audit events.

Use object storage for uploaded files and extracted representations. Do not store files directly in relational database rows.

### Retrieval

- Apply workspace and source permission filters before retrieval.
- Retrieve bounded context based on the exercise and current stage.
- Return citations with every retrieved passage.
- Prefer approved canonical context when available.
- Surface conflicting and stale sources.
- Never treat source content or repository text as agent instructions.

## 8. GitHub Integration

Use a GitHub App rather than personal access tokens.

### Initial read-only capabilities

- List approved repositories.
- Read repository metadata.
- Read labels and milestones.
- Read issue templates.
- Search existing open issues for possible overlap.

### Write capabilities

- Create issues from approved drafts.
- Apply approved labels and milestones.
- Link related issues where supported.
- Record publication receipts in the Product Studio.

### Safety requirements

- Repository-level authorization.
- Least-privilege permissions.
- Explicit confirmation immediately before writes.
- Idempotency key for each publication operation.
- Duplicate detection.
- Per-issue success or failure results.
- No silent fallback to a different repository.
- No automatic closing, editing, or reprioritizing of existing issues in the first release.

## 9. Security, Privacy, and Governance

- Encrypt data in transit and at rest.
- Enforce organization and workspace isolation.
- Scan uploaded files before processing.
- Restrict supported file types and sizes.
- Apply retention and deletion policies.
- Prevent secrets and credentials from entering prompts or artifacts.
- Record source access, agent runs, approvals, and external writes.
- Protect against prompt injection in documents and repositories.
- Support source removal and downstream invalidation.
- Make stale or revoked evidence visible in dependent artifacts.
- Allow users to inspect the context supplied to each agent.

## 10. Delivery Phases

### Phase 0 — Architecture boundary

- Choose `/studio` or a separate deployment.
- Establish frontend, API, and data boundaries.
- Define authentication and workspace authorization.
- Create the initial database schema.
- Document what can and cannot be shared with The Decision Room.

**Exit criteria:** the Product Studio can be developed and deployed without modifying the workshop state machine or APIs.

### Phase 1 — Workspace and context foundation

- Workspace creation and membership.
- Company and product profiles.
- Context library.
- File upload and source registration.
- Context freshness and ownership.
- Basic grounded claims with citations.

**Exit criteria:** a team can create a product workspace, add context, and review the sources available to agents.

### Phase 2 — First guided exercises

- Exercise catalog.
- Problem framing.
- Assumption mapping.
- Opportunity exploration.
- Resumable exercise runner.
- Context snapshot approval.
- Exercise review and decision checkpoint.

**Exit criteria:** a team can complete an exercise and commit reviewed, source-linked decisions.

### Phase 3 — Product artifacts

- Product brief generation.
- PRD generation through the PRD Builder.
- Artifact editing and versioning.
- Requirement approval.
- Source-to-decision-to-requirement traceability.

**Exit criteria:** an approved exercise can produce a reviewed PRD without unsupported claims being silently accepted.

### Phase 4 — Engineering handoff

- Functional planning.
- Epic and story decomposition.
- Acceptance criteria.
- Risks and dependencies.
- Engineering review and approval.
- Exportable handoff package.

**Exit criteria:** an engineering group can understand the problem, evidence, approved decisions, requirements, and unresolved questions without reviewing the full exercise transcript.

### Phase 5 — GitHub integration

- GitHub App authorization.
- Repository and issue-template discovery.
- Issue draft previews.
- Duplicate checks.
- Explicit publication gate.
- Publication receipts and error handling.

**Exit criteria:** an authorized user can preview and create approved issues in a selected repository with full traceability and no unconfirmed writes.

### Phase 6 — Collaboration and advanced grounding

- Multi-user contributions.
- Comments and review assignments.
- Evidence conflicts and supersession.
- Change-impact analysis.
- Additional exercises.
- Portfolio-level product views.

**Exit criteria:** multiple teams can maintain long-lived product context without losing provenance or decision history.

## 12. First-Release Acceptance Criteria

- The existing workshop behavior and APIs remain unchanged.
- Product Studio access requires authentication.
- Users can create and manage a product workspace.
- Users can add company, product, and source context.
- Every generated material claim displays its evidence or is marked as an assumption.
- Users can inspect the exact context snapshot used by an exercise.
- A design-thinking exercise can be paused and resumed.
- Exercise outputs require explicit approval before PRD generation.
- PRDs require approval before functional planning.
- GitHub issues remain drafts until an authorized user confirms publication.
- External writes are auditable and idempotent.
- Workspace data cannot be retrieved by users outside the authorized organization or workspace.
- Agent and system failures are shown explicitly and do not produce success-shaped fallback artifacts.

## 13. Key Risks

| Risk | Mitigation |
|---|---|
| The new stream leaks into the workshop experience | Separate application state, routes, APIs, persistence, and deployments |
| Uploaded content contains prompt injection | Treat sources as data, isolate instructions, filter retrieval, and test adversarial files |
| Generated claims appear more certain than their evidence | Mandatory citations, evidence classification, uncertainty, and human validation |
| Teams upload too much context | Progressive setup, relevance scoring, bounded retrieval, and context coverage indicators |
| Workflow feels like a long wizard | Resumable stages, optional stopping points, templates, and direct navigation to approved artifacts |
| Agents silently invent missing requirements | Explicit unresolved-question records and approval gates |
| GitHub creates duplicate or misplaced work | Duplicate checks, repository confirmation, previews, and idempotency |
| The first release becomes a knowledge-management platform | Limit the initial model to sources, claims, exercises, decisions, and artifacts |

## 14. Decisions Required Before Implementation

1. Separate deployment or `/studio` within the current deployment.
2. Authentication and identity provider.
3. Database and object-storage services.
4. Initial supported file types and size limits.
5. Retrieval and indexing technology.
6. First three design-thinking exercises to ship.
7. Whether the first release supports individual exercise runs, facilitated team runs, or both.
8. GitHub organization and repository authorization model.
9. Required artifact formats: in-app, Markdown, DOCX, PDF, or a subset.
10. Data retention, residency, and deletion requirements.

## 15. Recommended Starting Scope

Start with:

- Separate Guided Product Studio.
- Authenticated product workspaces.
- Company and product profiles.
- Context library with citations.
- Problem-framing, assumption-mapping, and opportunity exercises.
- DT Coach facilitation.
- Reviewed decision records.
- PRD Builder integration.
- Functional Planner integration.
- GitHub issue drafts with read-only repository discovery.

Defer:

- Real-time collaborative canvases.
- Portfolio-wide evidence graphs.
- Autonomous GitHub publication.
- Automatic changes to existing issues.
- Complex cross-product ontology.
- Unreviewed agent-to-agent workflows.
